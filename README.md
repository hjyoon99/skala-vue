# Vue Weather Dashboard

OpenWeatherMap API 를 Axios 로 연동하고, Pinia 로 상태를 관리하며, Element Plus 로 화면을
구성한 실시간 날씨 대시보드입니다. Vue.js 강의의 종합 실습 과제로 만들었고, 8장(Axios)과
9장(UI Library) 요구사항을 중심으로 구현했습니다.

저는 그동안 React 로만 개발해 왔고 Vue 는 이번 과제에서 처음 써 봤습니다. 그래서 이 문서에는
구현 기능과 실행 방법뿐 아니라, 개발하면서 막혔던 부분과 해결 과정, 그리고 React 와 비교해
비슷했던 점과 달랐던 점을 함께 정리했습니다.

**v6가 최종본입니다..!!!! v1-v5는 디렉토리에 있습니다.**

## 구현 기능

- **도시별 현재 날씨 대시보드** — 서울·수원·부산·인천·대구·제주 6개 도시의 현재 기온과 날씨,
  아이콘을 카드로 보여 줍니다. 6개 요청을 한꺼번에(병렬로) 불러옵니다.
- **도시 검색 및 추가** — 검색창에 도시 이름을 입력하면 좌표를 찾아 현재 날씨를 조회하고 카드
  목록에 추가합니다. 한글·영문 이름을 모두 받습니다.
- **목록 필터** — 이미 표시 중인 카드를 이름으로 걸러 냅니다. 필터 값은 주소창(`?q=`)에 저장되어
  새로고침해도 유지됩니다.
- **상세 페이지** (`/weather/:cityId`) — 현재 날씨에 더해 5일 예보와 대기질(미세먼지 등)을 함께
  보여 줍니다.
- **단위 전환** — 헤더의 스위치로 섭씨/화씨를 전환합니다. 값은 화면에서만 변환하므로 전환할 때
  API 를 다시 부르지 않습니다.
- **관심 지역** — 카드의 별 아이콘으로 등록/해제하며 브라우저에 저장됩니다. `/favorites` 에서
  모아 봅니다.
- **로딩·에러·빈 상태 처리** — 불러오는 중, 실패, 결과 없음을 각각 화면에 표시합니다. 한 도시
  요청이 실패해도 나머지는 정상적으로 나옵니다.
- **데모 데이터 대체** — `.env` 에 API 키가 없으면 가짜 데이터로 자동 대체되어, 키 없이도 화면을
  확인할 수 있습니다.

사용한 OpenWeatherMap API 는 현재 날씨(Current Weather), 5일 예보(Forecast), 대기질(Air
Pollution), 도시명→좌표 변환(Geocoding) 네 가지이며 모두 무료 범위입니다.

## 실행 방법

### 요구 사항

- Node.js `^20.19.0 || >=22.12.0`
- OpenWeatherMap API 키 (없어도 데모 데이터로 실행 가능)

### 1. 의존성 설치

```sh
npm install
```

### 2. 환경 변수 설정

```sh
cp .env.example .env
```

`.env` 파일을 열어 발급받은 키를 넣습니다.

```ini
VITE_OWM_API_KEY=여기에_키
```

- `.env` 는 `.gitignore` 에 등록되어 커밋되지 않습니다.
- 변수 이름은 반드시 `VITE_` 로 시작해야 합니다. (Vite 규칙)
- `.env` 를 고친 뒤에는 개발 서버를 껐다 켜야 합니다. Vite 는 서버가 뜰 때 한 번만 `.env` 를
  읽습니다.
- 새로 발급한 키는 활성화까지 10분에서 최대 두 시간 정도 걸립니다. 그 전에는 계속 401 이
  나옵니다.

### 3. 개발 서버

```sh
npm run dev
```

기본 주소는 <http://localhost:5173> 입니다.

### 4. 빌드 및 배포

```sh
npm run build     # dist/ 에 정적 파일 생성
npm run preview   # 빌드 결과 로컬 확인
```

`dist/` 폴더를 정적 호스팅(Vercel, Netlify, GitHub Pages 등)에 올리면 배포가 끝납니다.

### 5. 코드 정리

```sh
npm run lint      # 문법·규칙 검사 (자동 수정 포함)
npm run format    # Prettier 로 src/ 전체 포맷
```

## React 를 쓰다가 Vue 를 처음 써 보니

### 비슷해서 금방 적응한 부분

**컴포넌트를 파일로 쪼개는 방식.** React 에서 화면을 작은 컴포넌트 파일로 나누고 조립하던 것과
똑같았습니다. Vue 도 `.vue` 파일 하나가 컴포넌트 하나이고, 카드·검색창·예보 같은 조각을 따로
만들어 페이지에서 가져다 썼습니다. `WeatherHomeView` 가 `SearchBar` 와 `WeatherCard` 를
불러와 배치하는 구조는 React 에서 페이지 컴포넌트가 하위 컴포넌트를 렌더링하던 것과 다르지
않았습니다.

**폴더 나누는 기준.** React 에서 재사용 조각은 `components/`, 페이지 단위는 `pages/` 에
두던 습관이 있는데, Vue 도 `components/` 와 `views/` 로 같은 기준을 씁니다. `views/` 안의
컴포넌트만 라우터에 연결된다는 점도 React Router 에서 페이지 컴포넌트만 `<Route>` 에 걸던
것과 같았습니다.

**부모가 상태를 쥐고 자식은 표시만.** 목록 필터 값이나 선택된 도시 같은 상태는 페이지가 갖고,
`SearchBar` 나 `WeatherCard` 는 props 로 받아서 보여 주기만 합니다. React 에서 상태를 위로
끌어올리고(lift state up) props 로 내려 주던 패턴 그대로였습니다.

**props 로 데이터 내려 주기.** `<WeatherCard :city="city" :selected="..." />` 처럼 속성으로
데이터를 넘기고, 받는 쪽에서 `defineProps` 로 선언하는 방식이 React 의 props 와 사실상 같았습니다.
props 를 자식이 함부로 바꾸면 안 된다는 규칙도 동일했습니다.

**리스트·조건부 렌더링.** React 에서 `list.map(item => <Card ... />)` 하던 것이 `v-for`,
`{cond && <X/>}` 하던 것이 `v-if` 로 바뀐 정도였습니다. 리스트 항목마다 `key` 를 줘야 한다는
경고도 React 와 똑같이 나왔습니다.

**이벤트 핸들러.** `onClick={fn}` 이 `@click="fn"` 으로 바뀐 것뿐이라 거의 그대로 썼습니다.

**라우팅 개념.** React Router 를 써 본 적이 있어서 페이지를 경로에 매핑하고, 링크로 이동하고,
주소의 일부를 파라미터로 받는 개념은 익숙했습니다. `<Link>` 가 `<RouterLink>`, `useParams()`
가 `useRoute().params` 로 이름만 달랐습니다.

**스타일 격리.** React 에서 CSS Modules 로 스타일이 다른 컴포넌트에 안 새게 하던 것을, Vue 는
`<style scoped>` 한 줄로 해결해 줘서 오히려 편했습니다.

### 달라서 한참 헤맨 부분

**1. `.env` 를 고쳤는데 계속 "API 키가 유효하지 않습니다".**
키를 제대로 넣었는데도 401 이 떨어졌습니다. 처음엔 코드 문제인 줄 알고 한참 봤는데, 원인은
`.env` 를 저장한 시점이 개발 서버를 띄운 다음이었다는 것이었습니다. React(CRA) 는 `.env` 를
고치면 알아서 다시 읽었는데, Vite 는 서버가 뜰 때 한 번만 읽습니다. 서버를 껐다 켜니 됐습니다.
여기에 더해, 그날 새로 발급한 키라 활성화가 안 된 상태였고 점심먹고 오니 정상 작동되었습니다.

**2. 값은 바뀌는데 화면이 안 바뀝니다.**
React 의 `useState` 를 썼던 습관으로 그냥 변수를 만들어 값을 더했더니, 값은 바뀌는데 화면이 그대로였습니다.
Vue 에서 화면과 연결되는 값은 `ref()` 로 감싸야 하고, 코드 안에서는 `.value` 를 붙여서 읽고
써야 한다는 걸 예제를 다시 보고, AI를 활용하여 알았습니다. `useState` 는 `[값, 설정함수]` 형태라 딱 봐도 상태인
게 보였는데, Vue 의 `ref` 는 일반 변수랑 생김새가 같아서 처음엔 뭐가 상태인지 눈에 잘 안
들어왔고, `.value` 를 빼먹는 실수를 여러 번 했습니다.

**3. 자식 컴포넌트에서 부모 값을 못 바꿉니다.**
`SearchBar` 안에서 넘겨받은 값을 직접 바꾸려니 읽기 전용이라는 경고가 떴습니다. React 라면
`onChange` 콜백을 props 로 내려 주면 끝인데, Vue 는 자식이 부모에게 알릴 때 이벤트를 "쏘는"
방식이었습니다. 자식에서 `emit('update-query', 값)` 을 하고 부모에서 `@update-query` 로 받는
식입니다. React 는 그냥 함수를 넘기면 되는데 Vue 는 이벤트 이름을 선언하고 쏘고 받는 절차가 있어서 처음엔 번거롭게 느껴졌습니다.

**4. 전역 상태를 꺼냈더니 화면이 안 갱신됩니다.**
Zustand 처럼 스토어에서 값을 꺼내 쓰는 습관대로 `const { cities } = useWeatherStore()` 를
했더니, 처음 한 번만 그려지고 로딩이 끝나도 갱신되지 않았습니다. Vue 의 Pinia 는 이렇게 그냥
꺼내면 그 순간 값으로 고정된다고 해서, `storeToRefs()` 로 감싸야 했습니다. 반면 함수(액션)는
그냥 꺼내도 됩니다. "값은 `storeToRefs`, 함수는 그냥"이라는 규칙이 React 에는 없던 부분이라
어려웠습니다.

**5. `useEffect` 하나면 되던 게 여러 개로 나뉘어 있습니다.**
React 에서는 화면에 따라 뭔가 실행하는 일을 전부 `useEffect` 로 처리했는데, Vue 는 값이
바뀔 때 반응하는 `watch`, 다른 값에서 계산되는 `computed` 로 역할이 나뉘어 있었습니다.
처음엔 필터 결과 목록까지 `watch` 로 다시 계산하고 있었는데, "다른 값에서 나오는 값"은
`computed` 로 만드는 게 맞다는 걸 AI와 함께 이야기하면서 배우고 바꿨습니다. `computed` 는 원본이 안 바뀌면 계산을
다시 안 해서 더 낫다고 합니다.

**6. 폼 입력이 조금 더 짧습니다.**
React 에서 입력창은 `value` 와 `onChange` 를 항상 같이 써야 했는데, Vue 는 `v-model` 하나로
양쪽을 묶어 줍니다. 알고 보니 `v-model` 도 결국 `value` + 이벤트를 줄여 놓은 것이라, 필터
입력처럼 부모가 값을 쥐고 있어야 하는 경우엔 일부러 풀어서 React 처럼 단방향으로 썼습니다.

**7. UI 라이브러리 넣는 방식.**
React 에서 MUI 같은 걸 쓸 때는 필요한 컴포넌트를 하나씩 import 했는데, Element Plus 는
`app.use(ElementPlus)` 한 줄로 전부 전역 등록하는 방식이 기본이었습니다. 편하긴 했지만
빌드할 때 안 쓰는 컴포넌트까지 들어가서 용량 경고가 떴습니다. 강의 자료에도 같은 경고가
정상으로 나와 있어서 과제 범위에서는 그대로 뒀습니다.

### 전체적인 느낌

화면을 빠르게 만드는 데는 Vue 쪽이 확실히 마찰이 적었습니다. `v-for`, `v-if`, `v-model`,
`<style scoped>` 처럼 자주 쓰는 게 문법으로 들어와 있어서 코드가 짧아졌습니다. 대신 "이 값은
왜 반응하고 저 값은 왜 안 하지"를 판단하는 감각을 익히는 데 시간이 필요했고, 그게 잡히기
전까지는 React 습관대로 짰다가 조용히 안 되는 경우가 많았습니다. 컴포넌트를 나누고 props 로
데이터를 주고받는 큰 그림은 두 프레임워크가 거의 같았고, 상태를 다루는 세부 규칙에서 차이가
났습니다.

## AI 활용 내역

React 경험으로 판단할 수 있는 부분은 직접 정했고, Vue 고유의 문법과 익숙하지 않은 코드는 AI
(Claude)의 도움을 받았습니다. 어떤 부분을 어떻게 활용했는지 솔직하게 남깁니다.

### 직접 한 부분

- **기능 범위와 화면 구성 결정** — 어떤 도시를 기본으로 보여 줄지, 상세 페이지에 무엇을 넣을지,
  검색·관심 지역·단위 전환을 어떻게 동작시킬지 같은 판단.
- **컴포넌트/폴더 구조 설계** — 재사용 조각과 페이지를 나누고, 로직(스토어·API)과 화면을
  분리하는 큰 그림. React 에서 하던 방식 그대로라 직접 잡았습니다.
- **부모-자식 데이터 흐름 설계** — 어떤 상태를 페이지가 쥐고 어떤 걸 props 로 내려 줄지.
- **코드 검토 및 수정** — 생성된 코드를 그대로 붙이지 않고, 이해되지 않는 부분은 설명을
  다시 요청해 확인한 뒤 반영했습니다.

### AI 도움을 받은 부분

- **스타일링** — 각 컴포넌트의 `<style scoped>` CSS 와 Element Plus 레이아웃(`el-container`,
  `el-menu`, `el-card`, `el-descriptions` 등)의 배치. 디자인 감각이 부족해 전반적인 스타일은
  AI 가 잡아 준 것을 기준으로 조정했습니다.
- **Pinia 스토어 구조** — 여러 요청을 병렬로 부르는 처리, `storeToRefs` 사용, 데모 데이터
  대체 로직 등 Vue 쪽 관례가 필요한 부분.
- **Vue 고유 문법** — `computed` 의 getter/setter 로 스위치와 스토어를 잇는 방법, 라우트
  파라미터를 감시하는 패턴, `defineProps`/`defineEmits` 사용법 등.
- **응답 데이터 가공** — 3시간 단위 예보를 날짜별로 묶는 함수, 대기질 등급 계산 같은 유틸.
- **API 연결 방법** - 날씨 API를 연동하는 과정에서 데이터 형식 파악 및 연결 과정에서 어떤식으로 해야하는지 가이드를 요청하여 도움을 받았습니다.

### 활용 방식

새 기능을 붙이기 전에 먼저 "이건 어떤 개념이고 React 와 뭐가 다른지" 설명을 요청했고, 코드를
받은 다음에는 모르는 문법을 하나씩 물어보며 확인했습니다. `.env` 를 넣었는데 401 이 나던 문제도
증상을 설명하고 원인을 같이 찾는 식으로 해결했습니다. UI 라이브러리도 후보별 장단점을 정리받아
비교한 뒤 Element Plus 를 선택했습니다.

정리하면, **무엇을 만들지와 어떻게 구조를 잡을지는 직접 정하고, Vue 문법으로 옮기는 과정과
스타일은 AI 의 도움을 받아 채운** 방식이었습니다.
